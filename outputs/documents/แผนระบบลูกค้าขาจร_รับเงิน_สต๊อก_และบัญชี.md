# แผนเพิ่ม “ลูกค้าขาจร” พร้อมรับเงิน สต๊อก และบัญชี

## สรุปข้อกำหนด

เพิ่มช่องทางบันทึกลูกค้าขาจรแยกจากร้านค้า โดยมีสองประเภท:

- **จ่ายทันที**
- **แจกฟรี**

ข้อตกลงที่ล็อกแล้ว:

- ไม่สร้างร้านขาจรในตารางร้านค้า
- ไม่บันทึกชื่อหรือประเภทผู้รับ
- หนึ่งรายการเลือกน้ำแข็งได้หนึ่งชนิด
- เลือกเต็มถุง ครึ่งถุง หรือแบ่งตามยอดเงินได้
- พนักงานกรอกยอดขายเองทั้งหมด
- ยอดขาย ยอดรับ และเงินทอนเป็นจำนวนเต็มบาท ไม่มีสตางค์
- ขาจรต้องจ่ายครบ ไม่มีเครดิตหรือยอดค้าง
- แจกฟรีไม่บังคับเหตุผล เหลือเป็นหมายเหตุไม่บังคับ
- เต็มถุง/ครึ่งถุงตัดสต๊อกทันที
- แบบแบ่งตักรวมปริมาณที่ใช้ตอนปิดวัน
- รายการขายมีใบรับเงินและเลือกพิมพ์ได้
- รายงานรายร้านเพิ่มแถวสรุป **“ลูกค้าขาจร”**
- ยอดทั้งหมดต้องรวมในหน้าบัญชีและกระทบยอดเงินประจำวัน

หลักการสถาปัตยกรรมที่เพิ่มจากการทบทวน:

- `casual_transactions` เป็น operational source แยกจากร้าน แต่ยอดของมันต้องถูกรวมผ่าน balance และ accounting projections ชุดเดียวกับการขายร้าน
- ไม่สร้าง `shop_id` ปลอมหรือแถวใน `shops` เพื่อรองรับรายงาน
- `received_amount` คือเงินที่ลูกค้ายื่นหรือโอน, `sale_amount` คือยอดที่จัดสรรเข้าการขาย และ `change_amount = received_amount - sale_amount`
- ตัวเลข `cash_received` และ `cash_in` ใช้ `sale_amount` ไม่ใช้ยอดเงินสดที่ยื่นก่อนทอน
- การ void ไม่ลบประวัติและต้องมีหลักฐานเชิง audit ว่าคืนเงินเต็มจำนวนแล้ว
- `loose` ต้องมีการเชื่อมรายการต้นทางกับยอดใช้ตอนปิดวันอย่างตรวจสอบย้อนหลังได้
- RPC ทุกตัวเป็นช่องทางเขียนข้อมูลเพียงทางเดียว; authenticated client ไม่มีสิทธิ์ insert/update/delete ตารางขาจรโดยตรง

## หน้าพนักงาน

### จุดเข้าใช้งาน

หลังเลือกรอบแล้ว แสดงปุ่ม **“ลูกค้าขาจร”** เหนือส่วนค้นหาร้าน

หน้าขาจรใช้โครงสร้างเดียวกับหน้าบันทึกส่ง:

1. เลือกน้ำแข็งหนึ่งชนิด
2. เลือกรูปแบบ:
   - ระบุจำนวนถุง
   - แบ่งตามยอดเงิน
3. เลือก:
   - จ่ายทันที
   - แจกฟรี
4. ตรวจสอบและยืนยัน

รายการขาจรต้องผูกกับ:

- วันบริการ
- รอบที่เปิดอยู่
- พนักงานผู้บันทึก
- จุดถือครองสต๊อกของพนักงาน

แต่ไม่ผูกกับร้านหรือ `round_stop`

### ระบุจำนวนถุง

- ใช้ตัวเพิ่มลดทีละ `0.5`
- รองรับ `0.5, 1, 1.5, 2...` ถุง
- ตรวจไม่ให้เกินสต๊อกพนักงานและสต๊อกรวม
- แสดงยอดก่อนและหลังรายการ

สำหรับจ่ายทันที:

- พนักงานกรอกยอดขายเองเป็นจำนวนเต็มบาท
- ไม่ดึง ไม่คำนวณ และไม่ล็อกราคาจากราคากลาง
- ราคากลางของร้านไม่มีผลต่อขาจร
- ยอดขายต้องมากกว่า 0

สำหรับแจกฟรี:

- ไม่แสดงช่องยอดขายหรือการชำระเงิน
- หมายเหตุเป็นช่องไม่บังคับ
- ตัดสต๊อกตามจำนวนที่เลือก

### แบ่งตามยอดเงิน

ใช้สำหรับการขายหรือแจกที่น้อยกว่า 0.5 ถุง:

- ไม่กรอกจำนวนสินค้า
- ไม่ตัดสต๊อกทันที
- จ่ายทันทีมีปุ่มด่วน `5`, `10`, `20`, `30` บาท และช่องกรอกจำนวนเต็มบาท
- แจกฟรีบันทึกเฉพาะชนิดน้ำแข็งและหมายเหตุถ้ามี
- เก็บจำนวนครั้งและยอดเงินไว้ประกอบการปิดสต๊อก
- ปริมาณที่ใช้จริงจะรวมทีละ 0.5 ถุงตอนปิดวัน

### การรับเงิน

รองรับ:

- เงินสด
- โอนเงิน
- QR

กติกา:

- ยอดขาย ยอดรับ และเงินทอนต้องเป็นจำนวนเต็มบาท
- เงินสดรับเกินยอดขายได้ และระบบคำนวณเงินทอน
- โอนและ QR ต้องเท่ากับยอดขาย
- เงินสดไม่บังคับหลักฐาน
- โอนและ QR บังคับแนบสลิป
- หมายเหตุและเลขอ้างอิงไม่บังคับ
- ไม่อนุญาตรับเงินต่ำกว่ายอดขาย
- ไม่มีตัวเลือก “ยังไม่รับเงิน”, “เก็บท้ายวัน” หรือ “เครดิต”

หลังบันทึกสำเร็จ แสดง:

- เลขใบรับเงิน
- ยอดขาย
- ยอดรับ
- เงินทอน
- วิธีชำระ
- ปุ่มพิมพ์ใบรับเงิน
- ปุ่มบันทึกรายการใหม่

### ประวัติและยกเลิก

หน้าขาจรแสดงประวัติของพนักงานในวันนั้น:

- เวลา
- ชนิดน้ำแข็ง
- จำนวนหรือ “แบ่งตามยอด”
- จ่ายทันที/แจกฟรี
- ยอดขาย
- วิธีชำระ
- สถานะ active/voided

การยกเลิก:

- พนักงานยกเลิกรายการของตนเองได้ก่อนปิดสต๊อก
- ต้องกรอกเหตุผลการยกเลิก
- รายการขายต้องยืนยันว่าได้คืนเงินเต็มจำนวนแล้ว พร้อมวิธีคืนเงิน
- หากคืนด้วยโอนหรือ QR ต้องแนบหลักฐาน; เงินสดไม่บังคับหลักฐาน
- เต็ม/ครึ่งถุงที่ยกเลิกคืนผลต่อสต๊อก
- แบบแบ่งตามยอดที่ยกเลิกถูกตัดออกจากยอดสรุป
- ใบรับเงินเดิมเปลี่ยนสถานะเป็น voided โดยไม่ถูกลบหรือเขียนทับ
- หลังปิดสต๊อกแล้ว รายการเป็นแบบดูอย่างเดียว

## โครงสร้างข้อมูล

### ตาราง `casual_transactions`

เก็บหนึ่งแถวต่อรายการขาจร:

- `id`
- `service_date`
- `round_id`
- `source_stock_location_id`
- `ice_type_id`
- `transaction_kind`: `paid | free`
- `fulfillment_mode`: `measured | loose`
- `quantity numeric(12,1)` สำหรับ measured
- `sale_amount numeric(12,0)`
- `payment_method`
- `received_amount numeric(12,0)`
- `change_amount numeric(12,0)`
- `reference_number`
- `evidence_path`
- `note`
- `receipt_number`
- `idempotency_key`
- `request_fingerprint`
- `client_recorded_at`
- `recorded_by`
- `recorded_at`
- `status`: `active | voided`
- ข้อมูลผู้ยกเลิก เวลา และเหตุผล

ข้อบังคับ:

- measured ต้องมี quantity มากกว่า 0 และเพิ่มทีละ 0.5
- loose ต้องมี quantity เป็น null
- paid ต้องมี `sale_amount > 0`
- paid ต้องมีวิธีชำระ ยอดรับ และใบรับเงิน
- free ต้องมี `sale_amount = 0`
- free ต้องไม่มีข้อมูลการชำระ หลักฐานการชำระ หรือใบรับเงิน
- free ไม่บังคับ note
- จำนวนเงินทุกช่องต้องเป็นจำนวนเต็มบาท
- เงินสด: `received_amount = sale_amount + change_amount`
- โอน/QR: `received_amount = sale_amount` และ `change_amount = 0`
- ไม่อ้างถึง `shops`, `delivery_charges` หรือ `payment_allocations`
- `service_date` ต้องตรงกับวันของ `round_id` ด้วย composite foreign key หรือ constraint ที่เทียบเท่า
- RPC ต้อง derive `service_date`, `recorded_by` และ `source_stock_location_id` ฝั่ง server ห้ามเชื่อค่าจาก client
- paid ใช้ `sale_amount` เป็น allocated amount ของรายการเสมอ
- เงินสด: `received_amount` อาจมากกว่า `sale_amount`; `cash_in` และ `cash_received` เท่ากับ `sale_amount`
- โอน/QR: `received_amount = sale_amount`; ไม่มีเงินทอน

Index และ uniqueness ขั้นต่ำ:

- unique `idempotency_key`
- index `(service_date, status, recorded_by)`
- index `(service_date, status, source_stock_location_id, ice_type_id, fulfillment_mode)`
- index `receipt_number` แบบ unique เฉพาะ paid
- fingerprint ต้องครอบคลุม round, ice type, kind, mode, quantity, sale/payment fields, evidence path และ note

### ตาราง `casual_receipt_snapshots`

เก็บ snapshot ใบรับเงินแยกจาก `payment_receipt_snapshots` เพราะใบรับเงินเดิมบังคับความสัมพันธ์กับร้านและ `payment_allocations`:

- `transaction_id` เป็น primary key และ foreign key ไป `casual_transactions`
- `receipt_data jsonb` เป็น immutable
- `created_at`
- trigger ปฏิเสธ update/delete

### ตาราง `casual_refund_confirmations`

สร้างหนึ่งแถวแบบ immutable เมื่อ void รายการ paid:

- `transaction_id` เป็น primary key
- `refunded_amount` ต้องเท่ากับ `sale_amount`
- `refund_method`: เงินสด, โอนเงิน หรือ QR
- `reference_number` และ `evidence_path`
- `confirmed_by`, `confirmed_at`
- `idempotency_key` และ `request_fingerprint`

การยืนยันนี้บันทึกว่าคืนเงินเต็มจำนวนเรียบร้อยก่อน void ไม่ใช่ refund obligation แบบรอดำเนินการ ยอดบัญชีปัจจุบันจึงตัด SALE/REC ที่ voided ออกตาม semantics เดิม และไม่หัก confirmation ซ้ำเป็น `cash_out`

### การขยาย `daily_stock_uses`

- ขยาย `kind` จาก `refill` เป็น `refill | casual_loose`
- เพิ่ม `source_stock_location_id` แบบ nullable
- `refill` ต้องมี `source_stock_location_id = null`
- `casual_loose` ต้องมี `source_stock_location_id` และสร้างได้เฉพาะภายใน close v2
- เพิ่มตารางเชื่อม immutable `casual_loose_use_members(use_id, transaction_id)` เพื่อระบุว่า loose transaction ใดถูกรวมในยอดใช้ก้อนใด
- หนึ่ง loose transaction อยู่ได้ใน use เดียว

### Canonical stock projections

ต้องแก้แหล่งยอดเดิมโดยตรง ไม่สร้างยอดคู่ขนานเฉพาะหน้าขาจร:

- `stock_balance_at(service_date, location_id, ice_type_id)` หัก active measured casual ตาม quantity และหัก `casual_loose` use ตามจุดถือครอง
- `daily_aggregate_stock_balance_at(service_date, ice_type_id)` หัก active measured casual และ active `casual_loose` use
- `get_delivery_pos_context` และ context ขาจรอ่านยอดผ่านสองฟังก์ชันนี้ เพื่อให้ขายร้านและขายขาจรเห็นยอดเดียวกัน
- การ void measured ทำให้ projection ไม่นับรายการนั้นและยอดกลับคืนทั้งระดับพนักงานกับยอดรวม
- `accounting_aggregate_reconciliation_rows` แยก `legacy_refill` ออกจาก `casual_loose_use`; ห้ามรวม loose ไปแสดงในคอลัมน์ “เติมเดิม”
- ทุก write path ที่กระทบยอดต้องใช้ advisory lock ของ service date ชุดเดียวกับ `record_delivery` เพื่อป้องกันขายพร้อมกันเกินสต๊อก

### ใบรับเงิน

เพิ่ม immutable receipt snapshot สำหรับ casual transaction แบบ paid

- ใช้เลขเอกสาร `REC` จาก `document_counters` ชุดเดียวกับใบรับเงินร้าน
- Snapshot ถูกสร้างภายใน transaction เดียวกับการรับเงิน
- ไม่แก้ไข snapshot หลังออกเอกสาร
- การ void เพิ่มสถานะและเหตุผลด้านนอก snapshot เดิม

รูปแบบใบรับเงิน:

- ผู้ซื้อแสดง “ลูกค้าขาจร”
- แสดงวัน เวลา พนักงาน และจุดปฏิบัติงาน
- measured แสดงชนิดน้ำแข็งและจำนวนถุง
- loose แสดงชนิดน้ำแข็งและคำว่า “แบ่งขาย”
- แสดงยอดขาย ยอดรับ เงินทอน และวิธีชำระ
- ไม่แสดงราคาต่อหน่วย เพราะพนักงานกรอกยอดรวมเอง

## API และ Client Types

### RPC ใหม่

- `get_casual_transaction_context(round_id)`  
  คืนรอบ จุดถือครอง สต๊อก ชนิดน้ำแข็ง และประวัติขาจรวันนี้

- `record_casual_transaction(...)`  
  บันทึกสินค้า การรับเงิน ใบรับเงิน และผลต่อสต๊อกแบบ atomic

- `get_casual_receipt_snapshot(transaction_id)`  
  โหลดใบรับเงินเดิมเพื่อดูหรือพิมพ์ซ้ำ

- `void_casual_transaction(transaction_id, reason, refund_confirmation, idempotency_key)`
  ยกเลิกรายการก่อนปิดสต๊อก; paid ต้องสร้าง refund confirmation แบบ atomic ส่วน free ไม่รับ refund payload

- `close_daily_aggregate_stock_v2(...)`  
  ปิดสต๊อกพร้อมยอดใช้แบบแบ่งตัก แยกตามจุดถือครองและชนิดน้ำแข็ง

RPC บันทึกต้องตรวจ:

- ผู้ใช้ยัง active
- ผู้ใช้เป็นสมาชิกของรอบที่เลือก
- รอบและวันสต๊อกยังเปิด
- จุดถือครองเป็นของผู้บันทึก
- measured มีสต๊อกเพียงพอ
- จำนวนเงินเป็นจำนวนเต็ม
- วิธีชำระและหลักฐานถูกต้อง
- idempotency key ไม่ถูกใช้กับ payload อื่น

RPC บันทึกต้องทำตามลำดับ:

1. derive service date, user และจุดถือครองจากข้อมูล server
2. ล็อก service date ด้วย advisory lock ชุดเดียวกับ POS ร้าน
3. ตรวจยอดผ่าน `stock_balance_at` และ `daily_aggregate_stock_balance_at`
4. insert transaction
5. สำหรับ paid ออกเลข REC และสร้าง receipt snapshot ใน transaction เดียวกัน
6. เขียน audit log แล้วคืน transaction result กับ snapshot

RPC void ต้องล็อก transaction และ service date, ตรวจว่ายังไม่ปิดวันและ loose ยังไม่ถูกผูกกับ use, จากนั้นสร้าง refund confirmation สำหรับ paid และเปลี่ยน status เป็น voided ภายใน transaction เดียวกัน การ replay ด้วย key และ fingerprint เดิมต้องคืนผลเดิม; payload ต่างต้องถูกปฏิเสธ

### Type ฝั่งเว็บ

เพิ่ม:

- `CasualTransactionKind`
- `CasualFulfillmentMode`
- `CasualTransactionContext`
- `CasualTransactionPayload`
- `CasualTransactionResult`
- `CasualTransactionHistoryItem`
- `CasualReceiptSnapshot`

เพิ่ม gateway สำหรับโหลด context บันทึก ยกเลิก และพิมพ์ใบรับเงิน พร้อม recovery state และ idempotency เหมือนขายสดร้าน

เพิ่ม type สำหรับผลรายงานแยกจากร้าน:

- `CasualAccountingSummary`
- `CasualAccountingDailyRow`
- `CasualRefundConfirmation`
- ขยาย `AccountingTransactionType` ด้วย `FREE | CASUAL_USE`; `SALE | REC` ใช้ type เดิม
- ห้ามใช้ `AccountingShopSummaryRow` หรือสร้าง UUID ปลอมแทนลูกค้าขาจร

## การปิดสต๊อก

### รายการเต็ม/ครึ่งถุง

รายการ measured ที่ active ถูกหักจาก:

- สต๊อกจุดถือครองของพนักงาน
- สต๊อกรวมประจำวัน
- ยอดพร้อมส่งร้าน
- รายงานบัญชี quantity out

รายการ free แยกเป็น “แจกขาจร” และรายการ paid แยกเป็น “ขายขาจร”

### รายการแบ่งตามยอด

ระหว่างวันไม่หักปริมาณ

ตอนปิดวัน:

- แสดงเฉพาะพนักงานและชนิดน้ำแข็งที่มี loose transaction
- แสดงจำนวนรายการขาย
- แสดงยอดขาย
- แสดงจำนวนรายการแจกฟรี
- แสดงยอดนับจริงและส่วนต่างก่อนลงยอด loose
- หัวหน้าระบุยอดใช้รวมทีละ 0.5 ถุง
- ยอดใช้ถูกบันทึกแยกตาม `source_stock_location_id` และ `ice_type_id`
- ต้องไม่เกินสต๊อกก่อนปิด
- หากหลังรวม loose แล้วยังมีส่วนต่าง ใช้ workflow หมายเหตุส่วนต่างเดิม

เพิ่ม `casual_loose` เป็นชนิดใหม่ใน `daily_stock_uses` และเพิ่มจุดถือครองเพื่อให้ยอดรายพนักงานกับยอดรวมตรงกัน

### Contract ของ close v2

`get_daily_aggregate_stock_summary_v2(service_date)` คืน loose groups แยกตามจุดถือครองและชนิดน้ำแข็ง โดยแต่ละกลุ่มมี:

- จำนวน active paid/free loose transactions ที่ยังไม่ถูก aggregate
- ยอดขายรวม
- รายการ transaction IDs สำหรับตรวจสอบใน drawer
- `group_fingerprint` ที่คำนวณจาก ID, status และ recorded_at ของสมาชิก
- ยอดคงเหลือของจุดถือครองและยอดรวมก่อนลง loose use

`close_daily_aggregate_stock_v2(service_date, counts, loose_uses, note, idempotency_key, request_fingerprint)` รับยอดใช้ต่อกลุ่มและทำแบบ atomic:

1. ล็อก service date ก่อน แล้วจึงล็อก idempotency key และ loose rows ตามลำดับคงที่
2. ถ้ามี closure แล้ว: key/fingerprint เดิมคืน summary เดิม; payload ต่างถูกปฏิเสธ
3. โหลด active loose rows ใหม่และเทียบ `group_fingerprint`; หากมีรายการเพิ่ม/void ระหว่างเปิดหน้ากับกดยืนยัน ให้ reject เพื่อ refresh
4. ตรวจ quantity เป็นบวกและเพิ่มทีละ 0.5 และไม่เกินทั้งยอดจุดถือครองกับยอดรวม
5. สร้าง `daily_stock_uses(kind='casual_loose')` หนึ่งก้อนต่อ location/ice type
6. สร้าง `casual_loose_use_members` ครบทุก active loose row ของกลุ่ม
7. คำนวณ system quantity ใหม่หลังหัก loose แล้วจึงตรวจ actual counts และบังคับหมายเหตุส่วนต่าง
8. สร้าง closure, ปิดรอบ, เขียน audit log และ commit พร้อมกัน

เพิ่ม `request_fingerprint` ให้ daily aggregate closure เพื่อให้ replay ตรวจ payload ได้ ไม่ตรวจเพียง service date

RPC ปิดสต๊อกเดิมยังคงอยู่สำหรับ client เก่า แต่ต้อง:

- เปลี่ยนลำดับ lock ให้ล็อก service date ก่อนเหมือน v2 เพื่อไม่ให้ deadlock
- ปฏิเสธการปิดวันเมื่อมี active loose transaction ที่ยังไม่ถูก aggregate
- แจ้งให้อัปเดตแอปเพื่อใช้ `close_daily_aggregate_stock_v2`
- ยังทำงานเดิมทุกประการในวันที่ไม่มี loose transaction

## รายงานรายร้าน

แสดงแถวสังเคราะห์ **“ลูกค้าขาจร”** ในตารางรายร้าน โดยไม่สร้างแถวใน `shops` และไม่ยัดแถวนี้เข้า `AccountingShopSummaryRow[]`

เพิ่ม RPC แยก:

- `get_accounting_casual_summary(from_date, to_date, filters)`
- `get_accounting_casual_daily_matrix(from_date, to_date)`

หน้าเว็บโหลดสอง RPC นี้คู่กับ RPC ร้าน แล้ว render แถวขาจรเป็น footer row แยกจาก paginated shop rows จึงไม่มี `shop_id` ปลอม ไม่ถูกส่งเข้า `get_accounting_shop_daily_matrix(uuid[])` และไม่เปลี่ยน `total_count`

พฤติกรรมของแถว:

- แสดงท้ายตารางร้านเพียงหนึ่งครั้ง ไม่ขึ้นกับหน้าปัจจุบันของ pagination
- ไม่สังกัดอาคารหรือโซน
- ไม่นับรวมจำนวนร้าน
- ไม่กระทบจำนวนร้านซื้อแล้ว/ไม่ซื้อ/ยังไม่บันทึก
- ไม่มีวงเงินเครดิต วันครบกำหนด หรือลูกหนี้
- ยอดค้างและเกินกำหนดเป็นศูนย์เสมอ
- เมื่อกรองด้วยร้าน อาคาร หรือโซนเฉพาะ ให้ซ่อนแถวขาจร; ตัวกรองวันที่ พนักงาน ชนิดน้ำแข็ง และวิธีชำระยังใช้กับขาจรได้

คอลัมน์สรุป:

- ยอดขายช่วงที่เลือก
- เงินรับที่จัดสรรเข้าการขาย (`sale_amount`)
- เงินสด
- โอนเงิน
- QR
- เงินทอน
- จำนวนใบรับเงิน
- จำนวนรายการแจกฟรี
- จำนวนรายการแบ่งตามยอด
- สถานะ “รับครบ” เพราะขาจรไม่มีลูกหนี้

ในรายงานรายวัน แถวขาจรแสดงต่อวัน:

- ยอดขาย
- เงินรับที่จัดสรรเข้าการขาย
- จำนวนรายการขาย
- จำนวนรายการแจกฟรี

เมื่อกดแถว “ลูกค้าขาจร” เปิด drawer รายละเอียดแทน drawer ร้านค้า โดยแสดงรายการรายวันและเปิดใบรับเงินแต่ละรายการได้

การ export ต้องต่อ casual summary/daily section เพียงครั้งเดียวหลังร้านทั้งหมด โดยไม่เพิ่มจำนวนร้านและไม่ส่ง casual identifier เข้า API ที่รับ UUID ร้าน

## หน้าบัญชีและการกระทบยอด

ขยาย accounting transaction ledger ให้เพิ่ม:

- `SALE` — ขายขาจรทั้ง measured และ loose; loose มี quantity out เป็น 0
- `REC` — รับเงินขาจรหนึ่งแถวต่อใบรับเงิน
- `FREE` — แจกฟรีทั้ง measured และ loose; loose มี quantity out เป็น 0
- `CASUAL_USE` — ยอดแบ่งตักที่รวมตอนปิดวัน
- ไม่สร้าง type `VOID` แยก; SALE/REC/FREE เดิมคงอยู่ด้วย status `voided` และรายละเอียด refund confirmation

ทุกแถวขาจรใช้ `shop_id = null`, `shop_name = 'ลูกค้าขาจร'`, `source_table` ตามตารางต้นทาง และ route drawer จาก `source_table/source_id` ไม่ใช้ payment drawer ของร้าน

การนับ quantity out ต้องไม่ซ้ำ:

- paid measured: `SALE.quantity_out = quantity`
- free measured: `FREE.quantity_out = quantity`
- paid/free loose: SALE/FREE รายครั้งมี quantity out = 0
- ตอนปิดวัน: `CASUAL_USE.quantity_out = quantity` ของยอดรวมแต่ละ location/ice type

ผลต่อยอดบัญชี:

- ยอดขายขาจรรวมใน `effective_sales`
- active paid casual รวมใน `cash_received` ด้วย `sale_amount`
- `received_amount` ใช้แสดงยอดที่ยื่นหรือโอนเท่านั้น ไม่รวมใน `cash_received`
- เงินสดสุทธิคำนวณจาก `sale_amount` ไม่รวมเงินทอน
- โอนและ QR แยกตามวิธีชำระ
- แจกฟรีไม่เพิ่มยอดขายหรือเงินรับ
- voided ไม่รวมในยอดปัจจุบัน แต่ยังแสดงในประวัติ
- ขาจรไม่เพิ่มลูกหนี้หรือยอดค้าง
- measured เพิ่ม quantity out ทันที
- loose เพิ่ม quantity out เมื่อปิดวัน
- refund confirmation เป็นข้อมูล audit ของการ void และไม่ถูกหักซ้ำเป็น cash out

ตัวอย่างบังคับสำหรับทุก projection: ขาย 75 บาท รับเงินสด 100 บาท ทอน 25 บาท ต้องได้ `effective_sales=75`, `cash_received=75`, cash method total 75, `received_amount=100`, `change_amount=25`

เพิ่มการ์ดสรุปบัญชี:

- ยอดขายร้าน
- ยอดขายขาจร
- ยอดขายรวม
- รับเงินจริงจากร้าน
- รับเงินจริงจากขาจรที่จัดสรรเข้าการขาย
- เงินสดขาจร
- โอนขาจร
- QR ขาจร
- แจกฟรีขาจร
- เงินสุทธิรวม

Transaction drawer ของขาจรแสดง:

- เลขใบรับเงิน
- ชนิดและรูปแบบน้ำแข็ง
- จำนวนหรือ “แบ่งตามยอด”
- พนักงานและจุดถือครอง
- ยอดขาย ยอดรับ และเงินทอน
- วิธีชำระ
- หลักฐาน
- หมายเหตุ
- สถานะและเหตุผลยกเลิก
- จำนวน วิธี เวลา ผู้ยืนยัน และหลักฐานการคืนเงินสำหรับรายการ voided

## Offline และ Recovery

เพิ่ม `casual_transaction` ใน offline command contract โดยไม่แก้ความหมายของคำสั่ง v1 เดิม:

- คำสั่งเดิมยังใช้ `schemaVersion=1, payloadVersion=1`
- casual ใช้ `schemaVersion=1, payloadVersion=2`
- validator และ sync dispatcher ต้องรองรับทั้งสองเวอร์ชันพร้อมกัน
- ห้าม bump ค่า version กลางแล้วทำให้คำสั่ง v1 ที่ค้างอยู่ validate ไม่ผ่าน

Payload ประกอบด้วย:

- รอบและจุดถือครองที่คาดหวัง
- ชนิดน้ำแข็ง
- paid/free
- measured/loose
- quantity
- sale amount จำนวนเต็มบาท
- วิธีชำระ ยอดรับ และหลักฐาน
- note
- idempotency metadata
- `local_evidence_id` และ checksum สำหรับ draft ที่ยังไม่อัปโหลด หรือ remote evidence reference หลังอัปโหลดแล้ว

ตรวจ conflict:

- รอบปิด
- วันสต๊อกปิด
- สต๊อกไม่พอสำหรับ measured
- ผู้ใช้หรือจุดถือครองเปลี่ยน
- หลักฐานอัปโหลดไม่สำเร็จ
- idempotency payload ไม่ตรง

รายการ paid ที่ sync สำเร็จต้องคืน receipt snapshot ส่วน free ไม่มีใบรับเงิน

### การเก็บไฟล์หลักฐาน

ห้ามเก็บ `File` หรือ Blob ใน localStorage:

- เก็บ binary ใน IndexedDB แยก store ตาม `owner_id/local_evidence_id`
- localStorage recovery เก็บเฉพาะ ID, ชื่อไฟล์, MIME type, size, modified time และ SHA-256
- เมื่อออนไลน์ sync worker อัปโหลดไฟล์ไป path ที่ผูกกับ owner และ idempotency key ก่อนเรียก RPC
- หลัง command applied ให้ลบ local Blob; conflict/retryable ยังคง Blob ไว้; discard หรือ draft หมดอายุให้ลบทั้ง command และ Blob
- หาก IndexedDB quota ไม่พอ ต้องแจ้งก่อนรับรายการ ไม่ปล่อยให้ draft ดูเหมือนบันทึกสำเร็จ
- remote evidence ที่อัปโหลดแล้วแต่ RPC ไม่สำเร็จต้องถูกเก็บใน retry state และ reuse path เดิม ไม่อัปโหลดซ้ำ

Draft ต้องกู้คืนได้หลัง reload รวมถึง:

- ชนิดน้ำแข็ง
- จำนวนหรือรูปแบบ loose
- paid/free
- ยอดขาย
- วิธีชำระ
- ยอดรับ
- ไฟล์หลักฐานผ่าน `local_evidence_id` ที่ยังชี้ไปยัง Blob จริงใน IndexedDB หรือ remote path ที่อัปโหลดสำเร็จแล้ว
- หมายเหตุ

การ void รายการที่ sync แล้วต้องออนไลน์เพื่อยืนยันสถานะวันปิดและบันทึก refund confirmation แบบ atomic ส่วน casual command ที่ยัง pending สามารถ discard ในเครื่องพร้อมเหตุผลได้โดยไม่ออก REC และไม่กระทบสต๊อก server

## สิทธิ์และ Audit

- พนักงานบันทึกได้เฉพาะรอบเปิดและจุดถือครองของตน
- พนักงานดูและยกเลิกรายการของตนก่อนปิดวัน
- หัวหน้าและแอดมินดูรายการทั้งหมด
- หัวหน้าและแอดมินยกเลิกได้ก่อนปิดวัน
- หลังปิดวันรายการดูได้อย่างเดียว
- ทุกการบันทึกและยกเลิกเขียน audit log
- Receipt snapshot เป็น immutable
- Refund confirmation และ loose-use membership เป็น immutable
- ห้ามลบ casual transaction โดยตรง

- ตัวกรองร้าน/อาคาร/โซนซ่อน casual; ตัวกรองวันที่/พนักงาน/ชนิด/วิธีชำระยังคำนวณ casual ถูกต้อง
- ยอดขายและรับจริงตรงกับ transaction ที่ active
- method totals เงินสด/โอน/QR ตรง
- กรณีขาย 75 รับ 100 ทอน 25 แสดง cash received 75, received 100 และ change 25 ทุก projection
- outstanding ของขาจรเป็นศูนย์
- แจกฟรีไม่เพิ่มยอดขาย
- voided ถูกตัดจากยอดสรุปแต่ยังค้นย้อนหลังได้
- accounting reconciliation รวมยอดร้านและขาจรถูกต้อง
- quantity reconciliation รวม measured และ loose use ถูกต้อง
- `casual_loose` ไม่ถูกแสดงหรือส่งออกเป็น “เติมเดิม”
- paid/free loose มี ledger row รายครั้ง และ quantity out ปรากฏเฉพาะ `CASUAL_USE` ตอนปิดวัน

### Regression

- ส่งร้าน ขายสดร้าน เครดิต และรับชำระบางส่วนยังทำงานเดิม
- รายงานร้านจริงไม่เปลี่ยนยอด
- เลข REC ร้านและขาจรไม่ซ้ำ
- ปิดสต๊อกวันที่ไม่มีขาจรยังทำงานเดิม
- offline contract v1 และคำสั่งที่ค้างอยู่เดิมยังผ่านโดยไม่ต้อง migrate
- offline casual v2 ผ่านทั้ง paid/free, measured/loose, evidence retry และ discard cleanup
- build, unit, UI และ integration tests ผ่านทั้งหมด

## การปล่อยใช้งาน

1. ลง migration แบบ additive สำหรับตาราง, immutable triggers, RLS, receipt/refund, kind/location ของ stock use และ indexes โดยยังไม่เปิด feature
2. แก้ canonical stock/accounting projections พร้อม regression tests แล้วตรวจว่ายอดเดิมไม่เปลี่ยนในวันที่ไม่มี casual data
3. ปล่อย close v2, summary v2 และ close v1 guard พร้อม lock order เดียวกัน โดยยังไม่เปิด casual UI
4. ปล่อย frontend หน้าปิดสต๊อกและตรวจ client capability/telemetry ว่าผู้มีสิทธิ์ปิดวันใช้รุ่น v2 แล้ว
5. เปิด feature flag `casual_measured_enabled` ก่อน เพื่อทดสอบ REC, stock และ accounting โดยยังไม่มี loose
6. ปล่อยรายงาน synthetic footer, drawer, export และ offline contract v2
7. เปิด `casual_loose_enabled` หลัง close-v2 adoption ครบและ dry-run reconciliation ผ่าน
8. ตรวจสัปดาห์แรก:
   - ยอดขายขาจรเทียบใบรับเงิน
   - ยอดรับแยกเงินสด/โอน/QR
   - เงินทอน
   - รายการ loose เทียบยอดใช้ตอนปิดวัน
   - ส่วนต่างสต๊อก
   - รายการ void และ offline conflict

## สมมติฐานสุดท้าย

- พนักงานเป็นผู้กำหนดยอดขายขาจรเองทุกกรณี
- ระบบไม่ใช้ราคากลางกับขาจร
- จำนวนเงินขาจรไม่มีสตางค์
- ขาจรต้องจ่ายครบ ไม่มีลูกหนี้
- แจกฟรีไม่บังคับเหตุผล
- ขาจรหนึ่งรายการมีน้ำแข็งหนึ่งชนิด
- measured ใช้หน่วยขั้นต่ำ 0.5 ถุง
- loose ไม่ติดตามปริมาณรายคน
- loose ถูกสรุปปริมาณตอนปิดวัน
- loose ทุกแถวถูกผูกกับยอด use ที่สร้างตอนปิดวัน
- แถวขาจรในรายงานรายร้านเป็นแถวสังเคราะห์ ไม่ใช่ร้านจริง
- แถวขาจรส่งผ่าน RPC และ type แยก ไม่ใช้ `AccountingShopSummaryRow`
- การแก้ไขหลังปิดวันไม่อยู่ใน v1
