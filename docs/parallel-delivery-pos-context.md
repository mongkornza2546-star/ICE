# Parallel delivery POS reads

Migration `0257_parallel_delivery_pos_context.sql` adds `get_delivery_pos_context_part(uuid,text)` and `get_event_delivery_pos_context_part(uuid,text)`. Each accepts `stock` or `sale`.

- `stock` reads inventory quantities and the source. It skips payment-profile/credit-exposure queries and gates effective-price lookups off.
- `sale` reads effective prices and payment terms, including credit and VAT. It does not call either stock-balance function.

Both requests start concurrently when a shop opens. The gateway joins them by ice-type ID and verifies the stop, round, date and product sets before accepting the complete result. A partial response cannot enable submission. After ten seconds, the UI shows a slow-network notice while continuing to wait for the current request. A sixty-second hard deadline aborts both HTTP requests and releases single-flight for retry. A failed part also aborts its sibling. Responses after that deadline are discarded. The existing delivery writer remains authoritative for stock, prices, VAT and payment rules.

The live gateway always reads stock from the server. It neither caches completed POS contexts nor restores them from browser storage; concurrent reads for the same shop may share a request, but each subsequent visit starts a fresh read. The courier offline gateway described below wraps this live gateway. If either part fails, the whole read fails and retry is shown. Existing context can retain the draft and price labels, but its stock quantities are hidden and new delivery submissions are blocked until the refresh succeeds. Legacy stale contexts are also blocked. Idempotent replays of an unresolved delivery remain allowed, because the original write may already have reduced stock.

The workspace retains up to 50 shop previews in memory for the current user, date and round, keyed separately by POS/withdrawal mode and destination. Switching between POS and withdrawal preserves each mode's previews while invalidating its pending reads and open context. A preview contains the previously loaded product/price/payment labels, with stock quantities removed and the context marked stale. Returning to a visited shop shows that preview immediately and permits quantity drafting while a fresh read runs. Stock remains hidden and confirmation remains blocked until the complete live context arrives. A failed read keeps the preview and cart visible with a retry action; an unfinished keypad entry can be dismissed without changing the cart. Draft quantities are preserved after refresh; quantities above the new stock are flagged and must be corrected before submitting. The previews are discarded when the workspace unmounts or its gateway/user/date/round changes; they are not offline stock or a persistent cache.

The revisit regression occurred because `openCard` cleared the context and the review used the same loading flag to block both drafting and confirmation. Gateway freshness tests alone did not exercise that navigation experience. Workspace regressions now cover leaving and reopening a shop with a delayed request, editing above the previous stock, applying a new price and lower stock, submitting only the corrected live-priced order, failed refresh/retry, shop/user isolation and late responses. Existing live-stock and idempotent-retry checks remain applicable.

Review follow-up: mode was incorrectly part of the preview lifetime rather than its key, and keypad dismissal required committing an edit even when a failed read disabled editing. Regressions now cover both mode isolation and dismissal after failure. Outstanding collection balances use a separate reader: the shop list exposes a retry action, and focus, visible-page resume and reconnection retry failed balances without waiting for the normal five-minute foreground refresh interval. Concurrent resume signals share the outstanding retry; successful balances keep the normal refresh throttle. This fixes recovery from a failed read, not the underlying server/network cause of an individual failure.

Existing local `stock`/`pos` notifications and Supabase Realtime notifications refresh the open shop. A notification deferred during submission or while the workspace is hidden refreshes both the shop and employee holdings on resume. Holding-stock reads do not join an older in-flight read that may predate a withdrawal. Successful withdrawals apply the returned server state; successful deliveries refresh holdings before returning to the shop list. The transactional writer still checks actual stock under its database locks.

Stock invalidation also removes and aborts all pending POS reads, including other shops drawing from the same holding. The next visit starts immediately without joining a pre-write request. Late responses from aborted reads are rejected, and their cleanup cannot remove a newer request for the same shop.

Migration `0258_employee_stock_realtime_visibility.sql` adds a SELECT policy for active couriers to the already-published `stock_movements` table. They can observe movements on dates when they belong to a delivery round, affecting either the configured active courier-source truck or their own active holding. Shared-truck changes from another round on the same date are included because the stock ledger is date-based. Unrelated holdings/trucks and unassigned dates remain excluded; movement items and write permissions are not opened. Existing manager visibility remains unchanged.

Support is advertised as `pos_context_parts_version: 1` in the existing `get_employee_active_session` response, so no additional capability request is needed. Without that flag, the frontend uses the legacy RPC. Install migration 0257 before enabling the deployed frontend; installing the migration with the old frontend is also compatible. No production deployment was performed as part of this change.

Install migration 0258 as well for courier cross-device stock notifications. Local tests exercise the database SELECT policies and the frontend notification handlers; they do not establish a live Supabase WebSocket connection.

The migration derives the part readers from the installed full readers to retain all regular/event access checks, frozen event policies, admin truck routing, courier holding rules and closed-day rules. Future changes to either full reader must also update the part readers; reapplying this migration regenerates them and checks the expected source fragments.

Validation covers concurrent request start, fresh reads on revisiting a shop, rejection of saved stock on network failure, missing/mismatched parts, a failed request beside a stalled request, timeout/retry and late responses. Database tests compare combined parts with the full context, including event deliveries after closure, check permissions, and replace stock functions with failing probes to prove the sale request does not invoke them. These establish the parallel structure and removed work; they do not claim a measured production latency improvement.

## Courier offline stock refresh (2026-11-02)

The offline wrapper previously returned its IndexedDB snapshot even when the workspace requested `forceRefresh`. Realtime correctly notified the workspace, but clearing the live gateway cache did not refresh that snapshot. A reproduction delivered a `stock_movements` notification with remote stock at zero; the open POS continued displaying the saved 23 bags. Existing notification tests used the live gateway, while offline tests covered local projection/replay without crossing the Realtime-to-offline-read boundary.

Online foreground reads now use the live gateway when there are no pending commands. POS and holding reads do not wait for full offline preparation or the collection queue. Writes following those live reads use the existing guarded online writer, so newly received stock is validated by the server rather than against an older offline balance. Its durable request fence and stored confirmation preserve idempotent retries. Live payment-evidence uploads return the actual stored path to the form before the sale request is persisted; a transport failure retains the evidence and subsequent sale in the offline queue.

The runtime separately subscribes to stock/POS/payment/receivable changes to refresh the prepared snapshot. Known changes for other service dates are ignored, background attempts are throttled to once per 15 seconds, and each preparation makes at most two attempts when changes arrive during its reads. A superseded snapshot stays dirty for a later tick. Holdings and all POS contexts are installed together under the existing sequence/revision/lease checks. Installation publishes a notification marked `offline-snapshot`, which updates the workspace without invalidating and rebuilding the same snapshot again. Successful Realtime subscription/reconnection also requests a catch-up.

Offline reads, transport failures despite `navigator.onLine`, and unresolved queued commands use a valid prepared projection. POS identifies these balances with `offline_snapshot` and a visible notice. Authorization/business errors do not silently fall back to saved stock. Pending commands retain their original identities and projections; live reads recheck the queue before returning to avoid replacing a newly queued projection. Preparation first reconciles commands and cannot replace a snapshot while they remain unresolved. Conflicts and blocked/auth-required commands surface an error. The pending-delivery retry remains available even when current stock cannot be loaded. No commands are discarded or approved automatically.

For an existing red sync badge, open **ข้อมูลและรายการออฟไลน์** and inspect the command. A conflict needs the existing admin review flow before retry/discard; this frontend fix does not decide whether goods or money actually changed hands. Truck balances and employee holding balances are separate ledgers.

Regression coverage lives in `tests/employee-offline-realtime.test.tsx` (live reads/writes with an existing snapshot, the Realtime callback, rendered POS, bounded refresh under continuous changes, unavailable collection service, transport fallback with durable enqueue, evidence retention, conflict preservation, and offline reads), `tests/realtime-sync.test.tsx` (reconnection/cleanup), `tests/employee-delivery-review-navigation.test.tsx` (visible offline notice), and `tests/employee-online-recovery-form.test.tsx` (original-key replay when a current stock read fails). Validation uses mocked transport with real IndexedDB/runtime/UI code and the local database integration harness; it does not verify the pictured device or production WebSocket. No migration or production data change is required for this frontend fix; the existing 0258 policy remains a deployment prerequisite.

The broader UI run also found nine unrelated failures reproduced in a separate copy of unmodified HEAD: two in `history-receipt-corrections`, two in `role-router-pos-collection-recovery`, four in `employee-pos-payment-shortcut`, and one in `credit-vat`. These remain outside this fix.
