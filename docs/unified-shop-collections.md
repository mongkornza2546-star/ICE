# รวมบิลค้างในหน้ารับชำระ

## สาเหตุและพฤติกรรมใหม่

เดิม `get_collection_run_queue` แยกร้านเดียวเป็นคิวบิลทั่วไปและคิวต่อใบวางบิล
เมื่อมีใบวางบิล 1,800 บาท แล้วเพิ่มบิลย้อนหลัง 120 บาท หน้ารับเงินจากคิวทั่วไปจึงเห็นแค่ 120 บาท
การออกใบวางบิลไม่ได้ลดหนี้ แต่หน้าจอแสดงเพียงส่วนหนึ่งของหนี้ที่รับชำระได้

`get_shop_collection_queue` รวมคิวปกติของร้านกลับเป็นรายการเดียว และแนบเลขใบวางบิลไว้ที่แต่ละบิล
หน้ารับชำระจากลูกหนี้เครดิตและทางลัดหลังส่งของใช้คิวนี้เหมือนกัน
เลือกเฉพาะบางบิล เลือกข้ามใบวางบิล หรือเลือกทั้งหมดได้
บิลเครดิตที่ยังไม่ครบกำหนดและยังไม่ออกใบวางบิลยังใช้เงื่อนไขเดิม
คิวงานอีเวนต์ยังแยกตามบริบทงาน

## การรับเงินและประวัติ

- `record_shop_collection_payment` สร้าง payment และใบเสร็จเดียวใน transaction เดียว
  ใช้ writer เดิมตรวจสิทธิ์ หลักฐาน ยอดล่าสุด และการจัดสรรเงิน
- `payment_allocations.billing_statement_id` เก็บใบวางบิล ณ เวลารับชำระแต่ละบิล
  ทำให้รับเงินข้ามหลายใบวางบิลได้และไม่ต้องยกเลิกใบวางบิล
- รายการเดิมที่ไม่มี snapshot ใช้ `payments.billing_statement_id` ตามเดิม ไม่แก้ประวัติย้อนหลัง
- ยกเลิกรับเงินแล้วคืนยอดทั้งร้านและใบวางบิล ส่วนการแก้บิลหรือกลับรายการที่กระทบใบวางบิลฉบับทดแทนยังต้องยกเลิกฉบับทดแทนก่อน
- มี fingerprint แยกสำหรับ API ใหม่ เพื่อไม่ให้การ retry สลับกับ API เดิมแล้วบันทึกซ้ำ
  การรับเงินย้อนหลังใช้การตรวจวันที่และสิทธิ์ admin เดิม
- การยกเลิกใบวางบิลล็อกร้านก่อนแถวใบวางบิล ให้ตรงกับลำดับการล็อกขณะรับเงิน

## การนำขึ้นใช้งาน

1. ลง `supabase/migrations/0220_unified_shop_collections.sql` ก่อนปล่อย frontend ใหม่
2. ปล่อย frontend ที่เรียก API ใหม่และแสดงเลขใบวางบิลรายบิล
3. ตรวจร้านที่มีทั้งบิลในใบวางบิลและบิลทั่วไปว่ายอดรวม/จำนวนบิลตรงกับยอดที่ถึงกำหนดรับชำระ

API เดิมยังอยู่เพื่อรองรับ client เก่าและ retry ของใบเสร็จเดิม แต่ client เก่าจะยังแสดงคิวแยกจนกว่าจะโหลด frontend ใหม่
การย้อน frontend กลับยังใช้ API เดิมได้ ไม่ควรถอดคอลัมน์ snapshot หลังเริ่มรับเงินผ่าน API ใหม่

## การตรวจสอบ

ทดสอบใน `billing-statements.integration.test.mjs`, `credit-shop-vat.integration.test.mjs`,
`financial-payment-selection.test.tsx`, `unified-credit-collection.test.tsx` และ `collection-context.test.tsx`
ครอบคลุมยอด 1,800 + 120, จ่ายบางส่วน/ข้ามใบวางบิล, เงินทอน, void/reissue,
retry, สิทธิ์, รับเงินย้อนหลัง, ใบเสร็จ, VAT, อัปเกรดประวัติเดิม และแยกงานอีเวนต์

ผลตรวจ 12 ต.ค. 2569:

- `npm run build` ผ่าน
- ชุด Node ทั้งหมดผ่าน 254/255 กรณี; `i18n-static-copy.test.mjs` ไม่ผ่านเพราะคำแปลเดิมขาด 8 รายการใน `CollectionDesk.tsx`
- ชุด UI ทั้งหมดผ่าน 549/550 กรณี; `credit-vat.test.tsx` ไม่ผ่านเพราะ assertion แบบพิมพ์เดิมคาดเครื่องหมาย `:` และช่องว่างที่แบบพิมพ์ไม่มี
- รันสองกรณีที่ไม่ผ่านกับสำเนา `HEAD` ก่อนแก้แล้วให้ผลเดียวกัน
- ชุดฐานข้อมูลใบวางบิลและ VAT ที่เกี่ยวข้องรันซ้ำหลังแก้ขั้นสุดท้ายผ่านทั้งหมด

ยังไม่ได้ทดสอบ concurrent sessions บน PostgreSQL จริงในเครื่องนี้ เนื่องจาก Docker daemon ไม่ทำงาน
PGlite ใช้ยืนยัน transaction/constraints และการ retry แต่ไม่ใช่หลักฐานการทำงานพร้อมกันหลาย session
