# รวมบิลค้างในหน้ารับชำระ

## สาเหตุและพฤติกรรมใหม่

เดิม `get_collection_run_queue` แยกร้านเดียวเป็นคิวบิลทั่วไปและคิวต่อใบวางบิล
เมื่อมีใบวางบิล 1,800 บาท แล้วเพิ่มบิลย้อนหลัง 120 บาท หน้ารับเงินจากคิวทั่วไปจึงเห็นแค่ 120 บาท
การออกใบวางบิลไม่ได้ลดหนี้ แต่หน้าจอแสดงเพียงส่วนหนึ่งของหนี้ที่รับชำระได้

`get_shop_collection_queue` รวมคิวปกติของร้านกลับเป็นรายการเดียว และแนบเลขใบวางบิลไว้ที่แต่ละบิล
หน้ารับชำระจากลูกหนี้เครดิตและทางลัดหลังส่งของใช้คิวนี้เหมือนกัน
เลือกเฉพาะบางบิล เลือกข้ามใบวางบิล หรือเลือกทั้งหมดได้
บิลเครดิตที่ยังไม่ครบกำหนดและยังไม่ออกใบวางบิลยังใช้เงื่อนไขเดิม
คิวงานอีเวนต์รวมหลายวันต่อร้านที่เข้าร่วมงานเดียวกันด้วย migration
`20261027144741_unified_event_collections.sql` ตามรายละเอียดด้านล่าง

## ร้านอีเวนต์: รวมหลายวันต่อการเข้าร่วมงาน

ก่อนแก้ คิวอีเวนต์ใช้ `event_settlement_context_id` ซึ่งแยกตาม participation และวัน
ทำให้ยอด 120 บาทเมื่อวาน + 100 บาทวันนี้แสดงสองการ์ด และทางลัดจาก POS
ไม่เปิดหน้ารับเงินอัตโนมัติเพราะพบมากกว่าหนึ่งคิวของร้าน

ทั้งคิวปกติและคิวอ่านหลังปิดวันรวมเป็น `event-participation:<id>` พร้อม
`collection_scope = event_participation` และเรียงบิลตามวันที่ ร้านเดียวกันคนละงานยังแยกกัน
เมื่อกดรับชำระจาก POS จะเปิดหน้ารับเงินยอดรวมทันที เลือกจ่ายทั้งหมด บางบิล หรือบางส่วนได้
การ์ดแสดงช่วงวันที่และจำนวนบิลค้าง ส่วนบิลเดิมยังคงวันที่และข้อมูล snapshot ของตัวเอง

`record_event_collection_payment` สร้าง payment และ REC เดียวใน transaction เดียว
มีการตรวจสิทธิ์ วิธีรับเงิน หลักฐาน ยอดคงเหลือล่าสุด ยอดต่อบิล และ idempotency
ทั้งการรับเงินปกติและย้อนหลัง ใช้ล็อกวันที่เรียงตามวันและล็อกร้านร่วมกับ writer เดิม
การยกเลิกรับเงินคืนยอดทุกบิลในรายการตามเดิม

รายการใหม่มี `payments.event_collection = true` ซึ่งเปลี่ยนย้อนหลังไม่ได้
allocation และ refund ต้องอยู่ในร้าน/participation/config/policy เดียวกัน
แต่ต่างวันได้ โดยใช้ context แรกเป็น anchor ให้ history/receipt reader เดิม
ส่วนแต่ละ charge ยังคง context เดิม รายการเก่าและ `record_event_payment` เดิม
ยังบังคับ context เดียวเหมือนก่อนแก้ ไม่มีการย้ายยอดหรือแก้ใบเสร็จเดิม

API ใหม่ `get_daily_shop_collection_queue_v2` เรียกคิวเดิมเพื่อใช้กฎสิทธิ์ วัน และล็อกชุดเดิม
แล้วรวมเฉพาะแถวอีเวนต์ รูปแบบผลลัพธ์ของ API เดิมไม่เปลี่ยน APK/เว็บรุ่นเก่าจึงยังรับเงินรายวันได้
frontend ใหม่เรียก v2 และ fallback ไป API เดิมเฉพาะเมื่อ RPC ยังไม่มี (`PGRST202`)
ข้อผิดพลาดเรื่องสิทธิ์ วันที่ หรือเครือข่ายยังแสดงตามจริง

ลำดับปล่อยใช้งาน: ลง migration `20261027144741_unified_event_collections.sql` แล้วปล่อย frontend ใหม่
หาก frontend มาถึงก่อน migration จะใช้คิวรายวันชั่วคราวจนฐานข้อมูลพร้อม
ไม่ต้องบังคับ APK เก่าอัปเดตพร้อมกัน การย้อน frontend ยังใช้ API เดิมได้
ไม่ควรถอด scope/guard ของ payment ที่เกิดขึ้นแล้ว

ข้อแก้จาก review: การเปลี่ยนคิวเดิมทำให้ client เก่าส่งวันที่ null เข้า writer รายวัน
จึงแยก API ใหม่ และเพิ่มเทสต์เรียกคิวเดิมแล้วรับเงินครบทั้งสองวันจริง
อีกจุดคือ PostgreSQL numeric ยอมให้ NaN ผ่านเงื่อนไขยอด > 0 ได้
writer ใหม่จึงปฏิเสธ NaN/Infinity/-Infinity ของยอดรับ ยอดคงเหลือที่คาด และยอดจัดสรรทุกบิล
ก่อนคำนวณหรือบันทึก รวมถึงการรับเงินย้อนหลัง

ทดสอบ regression ที่ `unified-event-collection.integration.test.mjs` ด้วย migrations และ triggers จริง
ครอบคลุมส่งน้ำแข็ง/ค่าเช่าถังข้ามวัน ยอด 120 + 100 เงินทอน ใบเสร็จ ประวัติ ยกเลิก
จ่ายบางส่วน รับย้อนหลัง retry ต่างวันที่ ยอดเปลี่ยน การปนคนละงานผ่าน RPC/direct allocation
และสิทธิ์หลังปิดวัน ส่วน `event-pos-collection-scope.test.tsx` ตรวจทางลัด POS ของทุกบทบาท
และการส่งยอดทั้งหมด/บางบิล/บางส่วนผ่าน RPC เดียว
ชุดฐานข้อมูลใช้ PGlite; ยังไม่ได้ยืนยัน concurrent sessions บน PostgreSQL จริง
เพราะ Docker daemon ในเครื่องไม่ทำงาน

## การรับเงินและประวัติ

- `record_shop_collection_payment` สร้าง payment และใบเสร็จเดียวใน transaction เดียว
  ใช้ writer เดิมตรวจสิทธิ์ หลักฐาน ยอดล่าสุด และการจัดสรรเงิน
- `payment_allocations.billing_statement_id` เก็บใบวางบิล ณ เวลารับชำระแต่ละบิล
  ทำให้รับเงินข้ามหลายใบวางบิลได้และไม่ต้องยกเลิกใบวางบิล
- รายการเดิมที่ไม่มี snapshot ใช้ `payments.billing_statement_id` ตามเดิม ไม่แก้ประวัติย้อนหลัง
- ยกเลิกรับเงินแล้วคืนยอดทั้งร้านและใบวางบิล ส่วนการแก้บิลหรือกลับรายการที่กระทบใบวางบิลฉบับทดแทนยังต้องยกเลิกฉบับทดแทนก่อน
- มี fingerprint แยกสำหรับ API ใหม่ เพื่อไม่ให้การ retry สลับกับ API เดิมแล้วบันทึกซ้ำ
  การรับเงินย้อนหลังใช้การตรวจวันที่และสิทธิ์ admin เดิม
- การยกเลิกใบวางบิลล็อกร้านก่อนแถวใบวางบิล ให้ตรงกับลำดับการล็อกขณะรับเงิน

## การนำขึ้นใช้งาน

1. ลง `supabase/migrations/0220_unified_shop_collections.sql` ก่อนปล่อย frontend ใหม่
2. ปล่อย frontend ที่เรียก API ใหม่และแสดงเลขใบวางบิลรายบิล
3. ตรวจร้านที่มีทั้งบิลในใบวางบิลและบิลทั่วไปว่ายอดรวม/จำนวนบิลตรงกับยอดที่ถึงกำหนดรับชำระ

API เดิมยังอยู่เพื่อรองรับ client เก่าและ retry ของใบเสร็จเดิม แต่ client เก่าจะยังแสดงคิวแยกจนกว่าจะโหลด frontend ใหม่
การย้อน frontend กลับยังใช้ API เดิมได้ ไม่ควรถอดคอลัมน์ snapshot หลังเริ่มรับเงินผ่าน API ใหม่

## การตรวจสอบ

ทดสอบใน `billing-statements.integration.test.mjs`, `credit-shop-vat.integration.test.mjs`,
`financial-payment-selection.test.tsx`, `unified-credit-collection.test.tsx` และ `collection-context.test.tsx`
ครอบคลุมยอด 1,800 + 120, จ่ายบางส่วน/ข้ามใบวางบิล, เงินทอน, void/reissue,
retry, สิทธิ์, รับเงินย้อนหลัง, ใบเสร็จ, VAT, อัปเกรดประวัติเดิม และแยกงานอีเวนต์

ผลตรวจ 12 ต.ค. 2569:

- `npm run build` ผ่าน
- ชุด Node ทั้งหมดผ่าน 254/255 กรณี; `i18n-static-copy.test.mjs` ไม่ผ่านเพราะคำแปลเดิมขาด 8 รายการใน `CollectionDesk.tsx`
- ชุด UI ทั้งหมดผ่าน 549/550 กรณี; `credit-vat.test.tsx` ไม่ผ่านเพราะ assertion แบบพิมพ์เดิมคาดเครื่องหมาย `:` และช่องว่างที่แบบพิมพ์ไม่มี
- รันสองกรณีที่ไม่ผ่านกับสำเนา `HEAD` ก่อนแก้แล้วให้ผลเดียวกัน
- ชุดฐานข้อมูลใบวางบิลและ VAT ที่เกี่ยวข้องรันซ้ำหลังแก้ขั้นสุดท้ายผ่านทั้งหมด

ยังไม่ได้ทดสอบ concurrent sessions บน PostgreSQL จริงในเครื่องนี้ เนื่องจาก Docker daemon ไม่ทำงาน
PGlite ใช้ยืนยัน transaction/constraints และการ retry แต่ไม่ใช่หลักฐานการทำงานพร้อมกันหลาย session
