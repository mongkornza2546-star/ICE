# แผนแก้ไขบิลส่งของ การรับชำระ และการคืนเงิน

เอกสารนี้กำหนดพฤติกรรมเป้าหมายเมื่อพบว่าพนักงานบันทึกยอดส่งผิด ทั้งกรณีที่ยังไม่เก็บเงินและเก็บเงินแล้ว โดยต่อยอดจาก [Flow การส่งและรับชำระ](employee-delivery-payment-flow.md) และ [กติกาการทำงาน](phase-0/operating-rules.md)

สถานะ: **นำไปใช้แล้ว** ผ่าน migration `0128`–`0131` และหน้าจอแก้บิล/คืนเงิน

## ข้อสรุปสำคัญ

การกด “ยกเลิก” ต้องไม่ยกเลิกทั้งบิลส่งของและการรับเงินโดยอัตโนมัติ เพราะเป็นคนละเหตุการณ์ทางธุรกิจ

- **ยกเลิกรับเงิน** หมายถึงเงินรายการนั้นไม่ได้รับจริงหรือบันทึกรับเงินผิด บิลส่งของและยอดค้างยังอยู่
- **แก้ไข/ยกเลิกบิลส่งของ** หมายถึงจำนวนหรือชนิดสินค้าที่ส่งผิด ระบบต้องแก้ยอดขายและสต๊อก โดยไม่ลบหลักฐานการรับเงินจริง
- หากเก็บเงินแล้ว การแก้บิลต้องคำนวณผลต่างใหม่ ถ้ายอดใหม่สูงกว่าให้เกิดยอดค้าง ถ้ายอดใหม่ต่ำกว่าให้เกิดรายการรอคืนเงิน

ระบบต้องใช้ปุ่มและข้อความยืนยันแยกกันอย่างชัดเจน ห้ามใช้ปุ่ม “ยกเลิก” ปุ่มเดียวกับทั้งสองความหมาย

## หลักการ

1. รายการส่งสินค้า รายการเรียกเก็บ และรายการรับเงินจริงเป็นข้อมูลคนละชุด
2. เงินที่รับจริงแล้วห้ามหายไปเพราะมีการแก้บิลส่งของ
3. เอกสารที่ออกเลขแล้วห้ามแก้ทับหรือลบ ต้องเก็บฉบับเดิมพร้อมสถานะยกเลิก/ถูกแทนที่และเชื่อมไปยังรายการใหม่
4. การแก้ไขทุกครั้งต้องมีเหตุผล ผู้ดำเนินการ เวลา และ audit log
5. การแก้บิล การย้ายยอดจัดสรรเงิน การสร้างยอดค้างหรือยอดคืนเงิน และการปรับสต๊อกต้องสำเร็จใน transaction เดียวกัน
6. การกดยืนยันซ้ำด้วย `idempotency_key` เดิมต้องไม่สร้างรายการทดแทน ยอดค้าง หรือยอดคืนเงินซ้ำ
7. หลังปิดรอบหรือปิดวันแล้ว ห้ามเปิด snapshot เก่ากลับมาแก้ ให้ใช้เอกสารปรับปรุงแทน

## คำศัพท์

| คำ | ความหมาย |
|---|---|
| บิลส่งของ | `delivery_event` และ `delivery_charge` ที่เกิดจากการส่งหนึ่งครั้ง |
| รับชำระ | `payment` ซึ่งเป็นหลักฐานว่าได้รับเงินจริง |
| การจัดสรรเงิน | `payment_allocation` ที่ระบุว่าเงินรับหนึ่งรายการนำไปตัดบิลใดเท่าไร |
| บิลทดแทน | รายการส่ง/เรียกเก็บใหม่ที่สร้างเพื่อแทนรายการเดิมในช่วงที่ยังเปิด |
| เอกสารปรับปรุง | รายการผลต่างเพิ่มหรือลดที่สร้างหลังปิดรอบหรือปิดวัน |
| ภาระคืนเงิน | จำนวนเงินที่ต้องคืนร้านเมื่อยอดใหม่ต่ำกว่าเงินที่รับไว้ |

## ตารางการทำงาน

| สถานการณ์ | ผู้มีสิทธิ์ | วิธีดำเนินการ | ผลต่อเงิน |
|---|---|---|---|
| ยังไม่รับเงิน และรอบ/วันยังเปิด | พนักงานเจ้าของรายการล่าสุด, หัวหน้า, แอดมิน | ยกเลิกรายการเดิมและสร้างบิลทดแทน | ไม่มีผลต่อเงิน |
| รับเงินแล้ว และช่วงงานยังเปิด | หัวหน้า, แอดมิน | สร้างบิลทดแทนและย้ายการจัดสรรเงินภายใน transaction เดียว | เกิดยอดค้างหรือภาระคืนเงินตามผลต่าง |
| ปิดรอบแล้ว แต่วันยังเปิด | แอดมิน | สร้างเอกสารปรับปรุง และปรับยอดรวมประจำวัน | ไม่แก้ snapshot รอบ |
| ปิดวันแล้ว | แอดมิน | สร้างเอกสารปรับปรุงด้านการเงินและประวัติ | ไม่แก้ snapshot สต๊อกที่ปิดแล้ว |
| บันทึกรับเงินผิดและเงินไม่ได้รับจริง | ตามสิทธิ์ยกเลิกรับเงิน | ยกเลิกรับเงินพร้อมเหตุผล | บิลกลับเป็นค้างชำระตามยอดที่เหลือ |

## กรณีที่ 1: พบยอดส่งผิดก่อนรับเงิน

พนักงานแก้ไขได้เมื่อครบทุกเงื่อนไขต่อไปนี้:

1. เป็นผู้บันทึกรายการเดิม
2. เป็นรายการส่งสถานะใช้งานล่าสุดของ `round_stop` โดยเรียง `recorded_at DESC, id DESC`
3. รอบและวันยังเปิด
4. ยังไม่มีการจัดสรรเงินที่ใช้งานอยู่ผูกกับบิล
5. แก้ได้เฉพาะชนิดและจำนวนสินค้า ไม่สามารถเปลี่ยนร้าน สถานะร้าน เงื่อนไขชำระ ราคา หรือยกเลิกการขายทั้งหมด

เมื่อยืนยัน ระบบต้อง:

1. ตรวจสิทธิ์และเงื่อนไขซ้ำบนเซิร์ฟเวอร์
2. ตรวจจำนวนเป็นขั้นละ `0.5` และตรวจสต๊อกตามชนิด
3. สร้างรายการส่งและบิลทดแทน
4. ใช้ราคาที่ snapshot จากรายการเดิมสำหรับสินค้าชนิดเดิม
5. หากเพิ่มสินค้าชนิดใหม่ ให้ใช้ราคาที่มีผล ณ `service_date` เดิม
6. ยกเลิกรายการเดิมพร้อมเชื่อม `replaced_by`
7. คืนสต๊อกจากรายการเดิมและตัดสต๊อกตามรายการใหม่
8. เขียนเหตุผลและ audit log

หากต้องการยกเลิกการขายทั้งหมด ให้หัวหน้าหรือแอดมินเป็นผู้ดำเนินการ

## กรณีที่ 2: พบยอดส่งผิดหลังรับเงิน

พนักงานส่งห้ามแก้เอง ให้หัวหน้าหรือแอดมินตรวจสอบหลักฐานและดำเนินการผ่านคำสั่งแก้บิลแบบ atomic

ระบบต้อง:

1. ล็อกบิลเดิม บิลที่เกี่ยวข้อง รายการรับเงิน และการจัดสรรเงินที่เกี่ยวข้อง
2. สร้างบิลทดแทนจากยอดที่ถูกต้อง
3. ย้ายเฉพาะการจัดสรรเงินของบิลเป้าหมายไปยังบิลทดแทน
4. คง `payment` เดิมไว้ รวมถึงเลขที่ใบเสร็จ วิธีชำระ ผู้รับเงิน และเวลารับเงิน
5. เก็บภาพใบเสร็จเดิมแบบ immutable เพื่อให้พิมพ์ซ้ำได้ตรงกับวันที่ออก
6. บันทึกค่าก่อนและหลังของการย้ายการจัดสรรเงินใน audit log
7. ยกเลิกบิลเดิมและเชื่อมไปยังบิลทดแทน
8. คำนวณยอดคงเหลือหรือยอดคืนเงิน

### ผลต่างหลังแก้บิล

| ผลการแก้ | พฤติกรรม |
|---|---|
| ยอดใหม่เท่ากับเงินที่จัดสรร | บิลใหม่จ่ายครบ ไม่มีรายการเพิ่ม |
| ยอดใหม่มากกว่าเงินที่จัดสรร | จัดสรรเงินเดิมเข้าบิลใหม่และเปิดยอดส่วนต่างเป็นยอดค้าง |
| ยอดใหม่น้อยกว่าเงินที่จัดสรร | จัดสรรเท่ายอดบิลใหม่และสร้างภาระคืนเงินสำหรับส่วนเกิน |

ถ้าใบเสร็จหนึ่งใบตัดหลายบิล ระบบต้องย้ายเฉพาะส่วนของบิลที่กำลังแก้ ห้ามกระทบการจัดสรรของบิลอื่น

ถ้าบิลหนึ่งใบถูกชำระด้วยเงินหลายรายการ ให้ลดการจัดสรรจากเงินที่รับล่าสุดก่อนเมื่อเกิดส่วนเกิน เพื่อให้ตรวจสอบเส้นทางเงินได้แน่นอน

## ภาระคืนเงิน

ระบบไม่เก็บส่วนเกินเป็นเครดิตร้านหรือเงินรับล่วงหน้า ต้องสร้าง `refund_obligation` เสมอ

สถานะขั้นต่ำ:

- `pending` — ทราบยอดที่ต้องคืนแล้ว แต่ยังไม่ได้คืนจริง
- `settled` — คืนเงินครบแล้ว
- `voided` — ยกเลิกรายการคืนเงินจากการย้อนรายการแก้ไขที่ถูกต้องตามสิทธิ์

กติกา:

1. ภาระคืนเงินค้างไว้ข้ามวันได้
2. การคืนเงินจริงต้องระบุจำนวน วิธีคืน ผู้คืน เวลา และเลขอ้างอิงถ้ามี
3. เวอร์ชันแรกให้ชำระคืนเต็มจำนวนครั้งเดียว ไม่รองรับคืนบางส่วน
4. ห้ามยกเลิกรับเงินต้นทางขณะที่มีภาระคืนเงินหรือรายการคืนเงินที่เชื่อมอยู่
5. รายงานต้องแยกยอดรับรวม ยอดคืน และยอดรับสุทธิ
6. การชำระคืนต้อง idempotent และป้องกันการคืนซ้ำจากการกดซ้ำหรือทำงานพร้อมกัน

## การแก้ไขหลังปิดรอบหรือปิดวัน

### ปิดรอบแล้ว แต่วันยังเปิด

- สร้าง `delivery_charge_adjustment` เป็นผลต่างบวกหรือลบบนบิลล่าสุดในสายการทดแทน
- บันทึกรายการสินค้าที่ถูกต้องและผลต่างจำนวนใน `delivery_adjustment_items`
- snapshot ของรอบเดิมยังคงเดิม
- ผลต่างจำนวนถูกนำไปคำนวณยอดรวมและสต๊อกประจำวัน

### ปิดวันแล้ว

- สร้างเอกสารปรับปรุงด้านการเงินและประวัติเท่านั้น
- ห้ามเปลี่ยน snapshot สต๊อกสิ้นวันที่ปิดแล้ว
- หน้าประวัติต้องแสดงรายการเดิมและเอกสารปรับปรุงเชื่อมกัน ไม่แสดงเหมือนรายการเดิมถูกแก้ย้อนหลัง

ยอดเรียกเก็บที่ใช้ในคิวเก็บเงิน ลูกหนี้ และการตรวจรับชำระคำนวณจาก:

```text
effective_charge_amount = original_amount + ผลรวม adjustment ที่ใช้งานอยู่
```

การปิด `collection_run` เป็นขอบเขตอีกชุดหนึ่ง แยกจากการปิดรอบและปิดวัน ระบบต้องตรวจสถานะทั้งสามส่วนตาม flow ที่ดำเนินการ ห้ามใช้สถานะใดสถานะหนึ่งแทนทั้งหมด

## โครงสร้างข้อมูลเป้าหมาย

### `payment_receipt_snapshots`

เก็บข้อมูลใบเสร็จ ณ เวลาที่ออกแบบ immutable เพื่อให้การพิมพ์ซ้ำไม่เปลี่ยนตามการย้าย allocation ภายหลัง ต้องมีขั้นตอน backfill ใบเสร็จเดิมก่อนเปลี่ยนหน้าพิมพ์ให้อ่านจาก snapshot

### `payment_allocation_changes`

เก็บประวัติ append-only ของการย้ายยอดจัดสรร โดยมี payment, charge เดิม, charge ใหม่, จำนวน, เหตุผล, ผู้ดำเนินการ และเวลา

### `refund_obligations` และ `refund_settlements`

เก็บภาระที่ต้องคืนและหลักฐานการคืนเงินจริงแยกจาก `payments`

### `delivery_charge_adjustments`

เก็บผลต่างยอดเงินแบบ signed amount โดยอ้างบิลต้นทางและขอบเขตการปิดที่ทำให้ต้องใช้ adjustment

### `delivery_adjustment_items`

เก็บรายการสินค้าที่ถูกต้อง จำนวนเดิม จำนวนใหม่ ผลต่าง และราคาที่ใช้คำนวณ

ตารางใหม่ทั้งหมดต้องมี RLS สำหรับการอ่านตามบทบาท แต่การเขียนให้ทำผ่าน security-definer RPC ที่ตรวจสิทธิ์และเงื่อนไขครบถ้วนเท่านั้น

## ความจริงของข้อมูลการเงิน

ระบบใช้แหล่งข้อมูลเพียงชุดเดียวสำหรับสถานะปัจจุบัน:

- `payments` คือเงินจริงที่รับมาและไม่แก้ทับ
- `payment_allocations` คือการจัดสรรปัจจุบันของเงินจริง และย้ายได้เฉพาะภายใน RPC แก้ไขที่ตรวจสอบแล้ว
- `payment_receipt_snapshots` คือหลักฐานเนื้อหาใบเสร็จเดิมและไม่แก้ไข

ต้องรักษาสมการต่อไปนี้สำหรับ payment ที่ใช้งานอยู่:

```text
ผลรวม allocation ปัจจุบัน + ผลรวมภาระคืนเงินที่เกิดจาก payment = payment.allocated_amount
```

ไม่สร้าง “effective allocation view” ซ้อนบน allocation เดิม เพราะจะทำให้ trigger, validator, หน้าจอ และรายงานมองเห็นความจริงคนละชุด

## API/RPC เป้าหมาย

- `get_delivery_correction_context` — โหลดสถานะ สิทธิ์ ยอดเงิน และขอบเขตการปิด
- `preview_delivery_correction` — คำนวณบิลใหม่ ผลต่างสต๊อก ยอดค้าง หรือยอดคืนโดยยังไม่เขียนข้อมูล
- `apply_open_delivery_correction` — แก้รายการในช่วงเปิดและจัดการ allocation แบบ atomic
- `create_closed_delivery_adjustment` — สร้างเอกสารปรับปรุงหลังปิดรอบหรือปิดวัน
- `get_refund_queue` — อ่านรายการรอคืนเงินตามสิทธิ์
- `get_financial_refund_summary` — สรุปยอดรับรวม ยอดคืนจริง และยอดรับสุทธิตามวัน
- `settle_refund` — บันทึกการคืนเงินจริงแบบ idempotent

`void_payment` ต้องถูกจำกัดให้ใช้เฉพาะกรณีบันทึกรับเงินผิดและช่วงรับเงินยังเปิด และต้องปฏิเสธเมื่อ payment เชื่อมกับการแก้บิล ภาระคืนเงิน หรือการคืนเงินแล้ว

## หน้าจอเป้าหมาย

1. **พนักงาน — ประวัติวันนี้**: แสดงปุ่ม “แก้จำนวนส่ง” เฉพาะรายการที่ผ่านเงื่อนไข และอธิบายสาเหตุเมื่อแก้ไม่ได้
2. **หัวหน้า — รายละเอียดใบเสร็จ/บิล**: เลือกบิลที่ต้องแก้ ดู preview และยืนยันผลต่าง
3. **แอดมิน — ประวัติการซื้อร้าน**: แก้รายการช่วงเปิดหรือสร้างเอกสารปรับปรุงช่วงปิด
4. **แผงแก้ไขร่วม**: แสดงรายการเดิม รายการใหม่ ผลต่อสต๊อก ยอดค้าง/ยอดคืน และช่องเหตุผลก่อนยืนยัน
5. **การเงิน — รายการรอคืนเงิน**: แสดงร้าน บิล ใบเสร็จ ยอดที่ต้องคืน อายุรายการ และการบันทึกคืนเงินจริง

เวอร์ชันแรกใช้หน้าจอเดิมที่มีอยู่เป็นจุดเข้าใช้งาน ยังไม่สร้าง Transaction Ledger กลางจนกว่าจะมีความจำเป็นจากการใช้งานจริง

## ข้อความบนหน้าจอ

ใช้คำสั่งที่ระบุผลชัดเจน:

- “แก้จำนวนส่ง”
- “ยกเลิกบิลส่งของ”
- “ยกเลิกรับเงิน”
- “สร้างเอกสารปรับปรุง”
- “บันทึกคืนเงิน”

กล่องยืนยันต้องบอกผลกระทบ เช่น:

> บิลใหม่ 450 บาท เงินที่รับและจัดสรรแล้ว 400 บาท หลังยืนยันร้านจะมียอดค้างเพิ่ม 50 บาท ใบเสร็จเดิมยังคงอยู่

หรือ:

> บิลใหม่ 350 บาท เงินที่รับและจัดสรรแล้ว 400 บาท หลังยืนยันจะสร้างรายการรอคืนเงิน 50 บาท ใบเสร็จเดิมยังคงอยู่

## ลำดับการพัฒนา

1. เพิ่ม receipt snapshot และ backfill เอกสารเดิม พร้อมเปลี่ยนการพิมพ์ซ้ำให้อ่าน snapshot
2. เพิ่มตาราง audit การย้าย allocation, refund และ adjustment พร้อม RLS
3. สร้าง RPC สำหรับ context และ preview โดยยังไม่เปิดให้เขียน
4. สร้าง flow แก้บิลก่อนรับเงินสำหรับพนักงาน หัวหน้า และแอดมิน
5. สร้าง flow แก้บิลหลังรับเงิน รวมการย้าย allocation และการสร้างยอดค้าง/คืนเงิน
6. สร้าง refund queue และการบันทึกคืนเงินจริง
7. สร้าง closed-period adjustment และอัปเดตลูกหนี้ คิวเก็บเงิน รายงาน และประวัติ
8. จำกัด `void_payment` ตามกติกาใหม่ และปรับข้อความทุกหน้าจอไม่ให้สับสนระหว่างบิลกับเงิน
9. อัปเดต [กติกาการทำงาน](phase-0/operating-rules.md) หลัง implementation พร้อมใช้งานจริง

ให้เพิ่ม migration ใหม่หลัง migration ล่าสุด หลีกเลี่ยงการ patch function ด้วยการแทนข้อความแบบ dynamic และประกาศ function ฉบับสมบูรณ์ที่ตรวจสอบได้ชัดเจน

## เกณฑ์รับงาน

- ยกเลิกรับเงินแล้วบิลส่งของยังอยู่และยอดค้างกลับมาถูกต้อง
- แก้บิลที่ยังไม่รับเงินแล้วสต๊อก ยอดขาย และประวัติถูกต้อง โดยไม่เกิดข้อมูลซ้ำเมื่อ retry
- พนักงานแก้ได้เฉพาะรายการล่าสุดของตนที่ยังไม่รับเงิน และแก้ไม่ได้ทันทีเมื่อมีผู้รับเงินพร้อมกัน
- แก้บิลหลังรับเงินแล้ว payment และใบเสร็จเดิมไม่ถูกลบหรือแก้ทับ
- ยอดใหม่มากกว่าเดิมสร้างยอดค้างถูกต้อง
- ยอดใหม่ต่ำกว่าเดิมสร้างภาระคืนเงินถูกต้อง และคืนเงินซ้ำไม่ได้
- ใบเสร็จเดียวตัดหลายบิลแล้วการแก้บิลหนึ่งใบไม่กระทบบิลอื่น
- บิลเดียวรับเงินหลายครั้งแล้วระบบเลือกส่วนเกินจาก payment ล่าสุดตามกติกา
- การแก้จำนวน `0.5` กระสอบคำนวณราคา สต๊อก และผลต่างถูกต้อง
- หลังปิดรอบ ระบบไม่แก้ snapshot รอบ แต่ยอดรวมประจำวันสะท้อน adjustment เมื่อวันยังเปิด
- หลังปิดวัน ระบบไม่แก้ snapshot สต๊อกสิ้นวันและแสดง adjustment แยกในประวัติ
- การแก้ร้านเครดิตคำนวณยอดค้าง วงเงิน และสถานะระงับเครดิตจากยอด effective ถูกต้อง
- ผู้ไม่มีสิทธิ์เรียก RPC โดยตรงหรือเขียนตารางใหม่ผ่าน API ไม่ได้
- คำขอซ้ำและคำขอพร้อมกันไม่สร้างบิลทดแทน allocation ภาระคืนเงิน หรือการคืนเงินจริงซ้ำ

## กรณีที่ยังไม่รองรับในเวอร์ชันแรก

- การเก็บเงินส่วนเกินเป็นเครดิตร้านหรือเงินรับล่วงหน้า
- การคืนเงินบางส่วนหลายครั้ง
- การให้พนักงานส่งแก้บิลที่รับเงินแล้ว
- การเปลี่ยนร้าน เงื่อนไขชำระ หรือวันครบกำหนดผ่าน flow แก้จำนวนส่ง
- การเปิดรอบหรือวันเก่ากลับมาแก้ snapshot
- Transaction Ledger กลางสำหรับค้นหาทุกเหตุการณ์ในหน้าเดียว
